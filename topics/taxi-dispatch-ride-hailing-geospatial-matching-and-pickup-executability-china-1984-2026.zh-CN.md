# 从“站到路边等空车”到“把位置先发过去”：出租车调度、网约车、地理匹配与上车可执行性（中国，1984—2026）

> 研究切口：普通人要坐上一辆出租车，真正需要的不是“城市里有出租车”，而是 **一辆愿意接这一单的车与一个正在等车的人，能否在正确时间找到同一个上车点**。本文不写出租车/网约车行业通史，而研究 street hail、电话电召、GPS/车载终端、Web 订车、手机 App 与巡网融合怎样改变这种匹配，以及匹配机制怎样反过来改变通勤、照护、返乡就业、司机劳动和不会使用智能手机者的出行。

## 一句话结论

**移动互联网没有发明“远程叫车”。电话、无线电、调度中心、GPS 和车载终端早已在把乘客需求从街边身体信号转成可调度的信息。真正变化的是：乘客与空车从必须偶然出现在同一条街，逐渐变成可以把位置、目的地、时间和订单状态先送进系统，由系统尝试制造一次会合。**

但“系统显示有车”与“人真的上车”之间永远存在一条状态链：

```text
城市里有出租车/网约车
  ≠ 此刻附近有车
  ≠ 附近车辆处于可载客状态
  ≠ 司机愿意接这一单
  ≠ 叫车请求已提交
  ≠ 平台/调度中心已受理
  ≠ 某辆车已匹配
  ≠ 司机已确认
  ≠ 司机实际上向上车点移动
  ≠ 双方理解的是同一个上车点
  ≠ 车辆实际到达
  ≠ 乘客识别到正确车辆
  ≠ 乘客实际上车
  ≠ 行程开始计费
  ≠ 顺利到达目的地
  ≠ 最终费用已结算
```

本文把“一个没有事先认识司机的人，能否从当前位置稳定召来一辆实际接走自己的车”的能力称为：

> **pickup executability / 上车可执行性**

把“乘客位置与车辆位置能否在系统中互相成为可查询、可匹配对象”的能力称为：

> **geospatial addressability / 地理可寻址性**

把一个叫车方式的大量采用改变其他叫车方式可用性的现象称为：

> **dispatch adoption externality / 调度采用外部性**

## 1. 为什么这是 life-course 问题，不只是“打车方便”

仓库已有通勤专题已经指出，距离的成本至少包含钱、时间、注意力与失去的亲友邻近性。出租车/网约车进一步暴露了一个更细的约束：

> **一条道路存在，不等于人在需要离开时恰好能获得一辆车。**

这对很多生活状态并不边缘：

- 住在公交密度低的城市边缘；
- 夜班、早班、赶火车或赶飞机；
- 带孩子、老人、轮椅或大量行李；
- 生病去医院；
- 暴雨、降雪、极端高温；
- 临时加班以后错过末班公共交通；
- 初到陌生城市、不知道出租车通常在哪里候客；
- 司机本人把开车当作临时劳动、返乡就业或照护兼容职业。

因此需要把“有没有出租车”拆成：

```text
城市车数
-> 时空分布
-> 是否空载
-> 司机接单激励
-> 乘客入口
-> 位置表达
-> 匹配/派单
-> 到达
-> 实际上车
```

这条链任何一点失败，用户体验都是同一个结果：**我走不了。**

## 2. Internet 以前：最基本的匹配方式是身体和空车在街上相遇

### 2.1 北京 1980s：出租车“存在”与普通人“日常可负担”不是同一件事

2013 年《京华时报》回顾北京出租车 29 年变迁时，采访当年已在北京工作的建筑师郑实。他回忆，在 1984 年黄色“面的”大量出现前，北京出租车主要服务于酒店等场景，价格昂贵；他月收入只有几十元，即使“实在没办法”才会花 5 元打一次车。

来源：

- 2013-05-08，京华时报 / 央视网保存，《北京出租车29年变迁：从“打的梦”到“打车难”》：
  https://news.cntv.cn/2013/05/08/ARTI1367959176342994.shtml

证据等级：**C/B 边界（后来人物回顾 + 同期行业梳理）**。

它不能证明北京家庭的普遍打车频率，但提醒我们：

```text
出租车技术存在
  ≠ 普通工资家庭可频繁承担
```

Internet 史如果从“App 何时上线”开始，会漏掉更早的一层：**先要有一个足够大的、普通人偶尔能够承担的城市出租车市场，数字调度才有生活史意义。**

### 2.2 街边扬招是一种“低技术、实时、强共址”的协议

传统扬招实际上有自己的状态机：

```text
乘客走到允许停车且车辆看得到的路边
-> 观察顶灯/空车状态
-> 挥手
-> 司机看见
-> 司机愿意停
-> 车辆找到安全停靠位置
-> 双方口头确认目的地
-> 上车
```

它的优点是：

- 不需要账号；
- 不需要电话；
- 不需要智能手机；
- 不需要网络；
- 不需要预先暴露姓名和位置；
- 一旦空车就在眼前，匹配时延极低。

它的缺点同样结构性：

- 偏远小区里没有车经过，就没有可见供给；
- 高峰时所有经过车辆都可能已满；
- 雨雪天需求突然集中；
- 轮椅、行李等特殊需求只有车停下以后才能谈；
- 空车和乘客即使相距几百米，只要不在同一路线上，也互相“不可见”。

这可以称为：

> **co-location requirement / 共址要求**。

早期调度技术首先拆掉的不是“司机必须开车”，而是**乘客必须先在物理空间碰见司机**。

## 3. 海外前史：无线电出租车在 Web 出现几十年前就已经把“站街等车”变成远程预约

### 3.1 1951—1956 伦敦：无线电调度已经制造新的供需匹配，但司机仍会选择什么时候响应

《The Spectator》1958 年 3 月 7 日的同期文章记录：伦敦从 **1951 年**开始以无线电控制出租车；到 1956 年底已有 **1,005 辆**出租车安装无线电设备，平均每天约有 **4,000 次**呼叫。

但文章同样指出，系统并没有自动消除短缺：司机更倾向于在街面生意清淡时响应无线电呼叫；铁路终点站在多班列车同时到达时仍会突然短缺。

来源：

- The Spectator Archive, 1958-03-07, “Taxi”:
  https://archive.spectator.co.uk/article/7th-march-1958/9/taxi

证据等级：**A/B（同期杂志文章）**。

这条材料非常重要，因为它说明后来 App 时代的一大难题其实非常古老：

> **dispatch technology can expose demand, but it cannot by itself create willing supply.**

也就是：

```text
调度中心知道有人要车
  ≠ 附近司机愿意放弃其他生意去接
```

### 3.2 1953 伦敦：电话叫车也是大众 Web 以前很久的消费者前端

后来的伦敦资料回顾，Dial-a-Cab 的前身在 1953 年由 6 名司机组成合作组织，使公众可以**通过电话订出租车**；到 1990s 这类 radio circuit 已经发展为大型调度组织。

来源：

- The Standard, 2012-04-12, Dial-a-Cab history:
  https://www.standard.co.uk/hp/front/cabbies-may-get-ps9-000-windfalls-6329637.html
- UK Parliament, 2002–03 Transport Committee memorandum by Joint Radio Taxi Association：伦敦 radio taxi 自 early 1950s 提供即时和预约行程：
  https://publications.parliament.uk/pa/cm200203/cmselect/cmtran/390/390ap22.htm

证据等级：**B/C（行业/机构历史回顾）**。

因此全球共同谱系并不是：

```text
扬招 -> smartphone app
```

而至少是：

```text
街边扬招 / 站点
-> 电话 + 人工调度 + 无线电
-> 计算机辅助调度
-> GPS/车载数据终端
-> Web/SMS/WAP 前端
-> 智能手机双边定位与平台匹配
```

中国后来经历的并非全新的抽象问题，而是把一条更早的 dispatch lineage 与移动互联网、大规模智能手机、移动支付和平台劳动结合起来。

## 4. 中国 1995—2005：后台调度先数字化，普通乘客前端仍然可能只是打电话

### 4.1 北京：1995 年已存在电话撮合调度中心，但它不是“大众 App 的早期版本”

2024 年北京出租汽车调度中心负责人回顾，该中心成立于 **1995 年**，长期提供电话叫车撮合服务；今天仍保留 96106 和面向老年人的 95128 等入口。

来源：

- 2024-04-27，北京日报 / 人民网北京，《北京郊区电话打车成功率升至85%》：
  https://bj.people.com.cn/n2/2024/0427/c14540-40825685.html

证据等级：**C/B 边界（现存机构对自身沿革的回顾）**。

这一条只用来确认“1995 年北京已有电话调度机构”的存在，不把今天的 6 万余辆巡网融合系统倒灌回 1995 年。

### 4.2 2004 苏州：电话 + 话务员 + GPS + 电脑屏幕，已经是一套完整的数字后台

2004 年《扬子晚报》/新华日报系报道，苏州已有近 2,000 辆出租车安装 GPS。乘客拨热线以后，调度中心人员在电脑上搜索乘客附近空车；系统显示车牌、司机姓名和电话，再让乘客与驾驶员直接沟通具体位置。报道说正常调度过程约 1 分钟，车辆约 3 分钟后可到指定地点。

来源：

- 2004-09-01，《苏州出租车试行电话叫车》：
  https://news.sohu.com/20040901/n221827977.shtml

证据等级：**B+（同期报纸）**。

这条 workflow 很值得长期保留：

```text
乘客：普通电话
-> 人工话务员
-> 电脑 + GPS 搜索空车
-> 司机车载系统/电话
-> 乘客和司机再次口头校正位置
```

所以：

> **household Internet use is not required for Internet-era / digital dispatch to affect household mobility.**

一个从未上过 Web 的乘客，也可能因为调度中心背后的 GPS、计算机和通信网络而少等几十分钟。

### 4.3 2004—2005 上海：政策希望把“扫街找人”变成统一调度，但计划目标不能冒充实际采用

2004 年上海市交通部门公开提出逐步改变长期以扬招为主的出租车使用方式，计划到 2007 年把约 4.3 万辆出租车纳入统一调度平台，让市民通过**上网、电话或固定泊车点**用车；报道同时引用当时约 45% 的出租车空驶率。

2005-01-01，统一预约叫车电话 96965 正式启用，当时可电调约 2,000 辆出租车，计划到 2007 年覆盖全行业约 4.2 万辆。

来源：

- 2004-11-12，北京青年报 / 搜狐保存：
  https://news.sohu.com/20041112/n222949104.shtml
- 2005-01-01，解放日报 / 新浪：《上海出租车统一调度系统启用》：
  https://auto.sina.com.cn/news/2005-01-01/092393374.shtml

证据等级：**B+（同期媒体，含主管部门计划）**。

必须保留：

```text
planned platform coverage
  ≠ installed terminals
  ≠ online vehicles
  ≠ drivers responding
  ≠ completed passenger pickups
```

## 5. 2006：Web 订车已经能把一个路名送到车载终端，但“输入地址”本身就是新的劳动

2006 年 4 月，上海强生出租推出 `www.62580000.com` 网上即时订车。同期记者实际操作后，输入电话、姓名、车辆数量、上车路名、门牌和候车地点，2–3 分钟后获得车号，不到 12 分钟车辆到楼下。

报道描述的系统链是：

```text
Web 表单
-> GPS 地址解析
-> GPRS/CDMA 调度平台
-> 1.5 km 范围空车车载终端
-> 某车响应
-> Web 页面返回车号
-> 驾驶员到达后电话联系乘客
```

来源：

- 2006-04-02，《新民晚报》/新浪，《强生出租今起有网上订车》：
  https://news.sina.com.cn/o/2006-04-02/13598593326s.shtml
- 2006-04-10，东方网 / 新浪，《出租车可以通过网络预订 20分钟内到》：
  https://news.sina.com.cn/o/2006-04-10/12518659970s.shtml

证据等级：**B+（同期媒体，其中后者含记者实测 workflow）**。

### 5.1 这不是今天 App 的简单早期版

系统明确存在几个今天容易忽视的限制：

- 当时只接受临时叫车，不接受预约；
- 一次最多叫 3 辆；
- 地址依靠路名、路口、门牌字符串；
- 错别字或位置描述不精确可能使 GPS 搜索失败；
- “有车可供”才返回车号；
- 车不到仍需要拨打 62580000 人工处理。

所以 Web 先解决的是：

> **把一个地址字符串远程投入出租车调度系统。**

它还没有完全解决：

> **手机传感器自动知道我站在哪里。**

两者之间有非常重要的历史差异。

### 5.2 从“被看见”到“把自己的坐标说清楚”

扬招时代，乘客要做的是站到司机看得到的位置。

Web/电话调度时代，新的劳动变成：

```text
我到底在什么路？
最近的交叉口叫什么？
小区哪个门能停车？
这个门牌系统能不能识别？
司机从哪个方向过来？
```

这可以称为：

> **pickup-description labor / 上车点描述劳动**。

后来 GPS pin 减少了其中一部分，却从未完全消灭“地图点”和“现实可停车地点”的差异。

## 6. 2007：技术已经存在，不代表调度市场已经稳定成立

### 6.1 无锡：GPS 装了四年，司机仍可能退出“被调度”

2007 年《无锡日报》采访资深的哥黄联。他说：

> “我车上安装的 GPS 现在基本当成车载电话在用。”

报道回顾，无锡从 2003 年起为约 1,000 辆出租车免费安装 GPS，并承诺电话叫车 15 分钟内到达；四年后，调度中心可供调度车辆降到约 60 辆。

来源：

- 2007-11-27，《无锡日报》/新浪，《出租车“电话叫车”陷入尴尬 前景好困难多》：
  https://news.sina.com.cn/c/2007-11-27/090012976371s.shtml

证据等级：**B+（同期媒体 + 司机第一人称）**。

这是一个非常重要的反例：

```text
GPS installed
  ≠ driver participates in dispatch
```

也就是说，信息系统要成为生活基础设施，需要司机激励、叫车密度、空驶成本、收费和乘客守约共同成立。

### 6.2 2007 北京：电话叫车对轮椅老人有特别意义，但车辆物理条件仍然决定是否可执行

84 岁的龚太太向《北京晚报》反映，自己坐轮椅出门时经常遇到司机因装卸慢、后备箱装不下轮椅等原因拒载。报道建议可拨 68373399 或 96103 订车，让车到家门口；但司机同样指出部分旧车型后备箱有气罐，确实难以容纳轮椅。

来源：

- 2007-11-06，北京晚报 / 新浪，《轮椅老人打车难电话叫车解心烦》：
  https://news.sina.com.cn/c/2007-11-06/143312855247s.shtml

证据等级：**B+（同期个人材料）**。

因此：

```text
remote booking
  ≠ accessible vehicle
```

电话可以把需求提前说出去，但它不会自动改变后备箱体积、轮椅升降设备和司机服务能力。

2008 年北京无障碍出租车的同期体验报道则记录，一通预约电话后约 40 分钟，无障碍车辆开到乘客面前，车内有轮椅升降装置。

- 2008-06-27，人民日报海外版 / 搜狐：
  https://2008.sohu.com/20080627/n257775628.shtml

这说明**“特殊车辆能否被远程寻址”本身就是无障碍的一部分**。

## 7. 2005—2012 的扩张型未来：从“车经过我”到“我把需求广播给周围的车”

这一阶段的核心并不是 App 已经统治城市，而是多个入口并存：

```text
扬招
+ 候客站
+ 公司电话
+ 城市统一电召
+ 短信
+ Web 表单
+ GPS/车台
+ 最早的智能手机 App
```

### 7.1 城市边缘先受益，因为“等一辆车随机经过”的概率最低

2005 年济南一项市民采访里，住在较偏住宅区的王女士希望有叫车服务，因为门口正规出租车少、黑车多；住在繁华路段的刘先生也说，家里有急事时，如果打个电话就能让出租车直接到楼下，就不用先跑到路边等。

来源：

- 2005-10-28，生活日报 / 新浪，《在家叫辆车为何这么难》：
  https://finance.sina.com.cn/roll/20051028/0733372245.shtml

证据等级：**B+（同期市民第一人称）**。

2007 年上海南汇又因为边缘城镇、小巷居民门口经常没有出租车经过，为 200 辆区域出租车装 GPRS 终端并开通电话叫车试点。

- 2007-11-05，新闻晚报 / 新浪：
  https://news.sina.com.cn/s/2007-11-05/132412848193s.shtml

这里真正新增的是：

> **low-density pickup portability / 低密度地点上车可携带性**。

一个人不必先走到“出租车自然愿意经过的地方”，调度系统试图把车辆短暂地搬到需求位置。

### 7.2 2012：智能手机第一次把“我在哪”变成消费者终端可以持续参与的匹配状态

2012 年 10 月《钱江晚报》记录杭州用户通过“快的打车”叫车：一名微博用户称国庆期间试了两次均成功；记者当晚在浙大紫金港测试，在加价条件下几秒内有司机响应，不加价则等待更久。

来源：

- 2012-10-09，钱江晚报 / 中新网，《多加三五块立马打到车 两成用户愿意加钱打车》：
  https://www.chinanews.com/auto/2012/10-09/4233192.shtml

证据等级：**B+（同期用户 + 记者测试）**。

这里新的并不是“有一个网页可以预约车”，而是：

```text
乘客手机位置
+ 司机手机位置
+ 两边同时在线
+ 订单广播/抢答
+ 目的地与加价信息
```

开始组成一个低成本、两边都携带的匹配网络。

但 2013 年北京的主管部门已经明确提醒：手机 App 暂时不能准确查询周边空驶车辆；这种精准服务依赖车辆定位数据传输及时性、车辆状态准确性以及管理制度，而不是“开发一个软件”就能解决。

来源：

- 2013-01-01，北京青年报 / 新浪，《打车APP：出租青睐加价招车 路边乘客遇冷》：
  https://auto.sina.com.cn/news/2013-01-01/12231084785.shtml

这条边界必须永久保留：

> **GPS coordinate != executable vacant-car inventory**。

## 8. 2013—2014：平台把司机的“下一单判断”公开化，也改变了街边扬招的基线

### 8.1 2013 的哥董师傅：同一辆车同时生活在“扫街、电召、打车软件”三套市场里

2013 年《北京青年报》跟随的哥董师傅记录完整一天。早高峰他仍靠扫街接活；之后收到 96106 电召订单，却因接客点约 2 公里且方向相反、空驶成本太高而放弃。手机上的嘀嘀则不断语音播报周围乘客的位置和目的地。

董师傅说自己使用嘀嘀三个月，接了 77 单；他会综合判断：

- 到乘客位置有多远；
- 是否要调头；
- 路上堵不堵；
- 乘客会不会等得及；
- 目的地是否容易空驶返回；
- 是否顺着自己早晨从通州出车或晚间回家的方向。

来源：

- 2013-06-06，北京青年报 / 新浪，《的哥讲述我不愿意接电召原因：不敌空驶成本》：
  https://news.sina.com.cn/c/2013-06-06/000027326134.shtml

证据等级：**A/B 边界（同期跟车观察 + 司机第一人称）**。

这条材料极其重要：

> App 没有创造司机的经济判断，它把原来主要靠司机看街、看区域经验完成的判断，部分提前到“接单前的信息界面”。

因此出现：

> **pre-pickup route selectivity / 上车前线路选择性**。

### 8.2 “有司机抢单”仍不等于“预约可靠”

同一报道里，林小姐通过统一电召预约第二天机场用车，两个小时没人联系后取消，却随后收到八九十条“约车成功”短信和多名司机电话。

这说明早期聚合调度还可能出现：

```text
passenger cancellation
  != all downstream driver copies cancelled
```

也就是非常典型的**分布式状态不同步**。

### 8.3 2014：数字订单开始挤压非数字乘客，技术采用产生外部性

2014 年北京一名杂志社职员刘鹏向记者抱怨，自己好不容易拦到车，司机却要求加价；司机同时刷快的和嘀嘀。另一个从上海到北京出差不到 20 天的徐毅称，连续三次下班打车都被告知已有软件预约，并担心如果司机都转向软件，非智能手机用户会越来越难打车。接受采访的出租司机也承认，这种群体确实可能更难打车。

来源：

- 2014-01-23，北京青年报 / 人民网，《打车软件致司机加价才肯走》：
  https://mobile.people.com.cn/n/2014/0123/c183175-24203793.html

证据等级：**B+（同期乘客与司机第一人称）**。

上海同期则出现老人就医后在寒风中扬招 30 分钟仍打不到车的报道，司机解释用软件接单更“高效”、还能获得补贴。

- 2014-02-24，法制日报 / 中新网：
  https://www.chinanews.com/df/2014/02-24/5873722.shtml

同年上海监管部门一度禁止出租车在早晚高峰用打车软件约车，理由之一就是软件冲击传统扬招并影响市场公平与安全。

- 2014-02-26，中新社 / 人民网：
  https://politics.people.com.cn/n/2014/0226/c70731-24474876.html

因此必须加入：

> **dispatch adoption externality / 调度采用外部性**。

一项叫车技术的价值不是只对“使用者自己”发生。司机总时间有限，如果数字订单改变司机去哪儿、接谁、是否停下，那么**没有智能手机的人面对的街面供给也会改变。**

### 8.4 补贴说明“匹配系统”同时也是激励系统

2014 年嘀嘀/快的把移动支付与司机、乘客每单补贴绑定，甚至出现做假单骗补贴的公开讨论。

来源：

- 2014-01-27，北京青年报 / 人民网：
  https://finance.people.com.cn/n/2014/0127/c70846-24240560.html

这进一步证明：

```text
order record
  != physical passenger trip
```

只要平台奖励“订单完成”这个数据库状态，参与者就可能尝试制造数据库里的完成，而不制造现实里的乘车。

## 9. 2015—2019 的拥堵型未来：从“能叫到车”转向“平台同时管理价格、安全、司机身份和劳动时间”

### 9.1 2016：网约车被正式定义成“互联网整合供需信息的非巡游预约出租服务”

2016 年七部门发布《网络预约出租汽车经营服务管理暂行办法》，自 2016-11-01 起施行。文件把网约车定义为以互联网技术为依托构建服务平台、整合供需信息，使用符合条件车辆和驾驶员，提供**非巡游的预约出租汽车服务**。

来源：

- 交通运输部等七部门，2016 年第 60 号令：
  https://www.cac.gov.cn/2016-07/28/c_1119297794.htm

证据等级：**A（正式部门规章）**。

这个定义非常适合生活史，因为它明确把两套世界拆开：

```text
巡游出租：车在街上成为“空车”，乘客可扬招
网约出租：车辆在平台上成为“可预约供给”，乘客先提交数字需求
```

现实中两者可以混合，但权威状态并不相同。

### 9.2 2018：安全事故迫使“匹配”加入身份、录音、紧急联系人和时段门禁

2018 年重大安全事件之后，滴滴一度在中国大陆暂停 23:00—05:00 的出租车、快车、优享、拼车等深夜服务，并上线/强化一键报警、紧急联系人、行程分享、录音、司机每日出车前安全考核、人脸识别等措施。

来源：

- 2018-09-05，人民网：
  https://it.people.com.cn/n1/2018/0905/c1009-30272482.html

证据等级：**B（平台措施经媒体报道）**。

这时“上车可执行性”已经不再只是：

```text
附近有没有司机？
```

还包括：

```text
这个账号对应的是不是这个人？
这辆车是不是页面上那辆车？
这个时段平台是否允许创建订单？
紧急情况下行程轨迹能否被第三方取得？
```

2018 年《法制日报》暗访还发现过 App 显示车辆与实际接车车辆不一致的“马甲车”现象。

- 2018-03-23，法制日报 / 人民网：
  https://industry.people.com.cn/n1/2018/0323/c413883-29884718.html

因此必须保留：

```text
platform driver profile
  != person currently driving
platform vehicle record
  != vehicle physically arriving
```

### 9.3 2019 苏诗东：网约车成为“返乡 + 照护 + 工作”重新组合的一条真实生命路径

《工人日报》2019 年采访 46 岁的苏诗东。他和妻子早年外出广东打工；2015 年底因父母年纪大、经常生病无人照料，女儿又面临升学，夫妻决定回重庆。他把打工积蓄用于住房和车辆，开始跑网约车。

他的生活不是“自由职业浪漫故事”：

- 一周跑 6 天；
- 下午约 1 点出车，午夜回家；
- 自述每天接近 12 小时；
- 平台奖励已经明显减少；
- 熟悉地区较好跑，陌生地区常遇到乘客定位不准；
- 需要网约车驾驶员证、挂靠等合规成本；
- 他仍把可以自己安排时间、家里有事可以少跑几单视为重要优点。

他说，有了社保会让他觉得这是一份“稳定、有保障的工作”。

来源：

- 2019-04-11，《工人日报》/ 人民网：
  https://acftu.people.com.cn/n1/2019/0411/c67583-31024654.html

证据等级：**B+（同期完整人物采访）**。

它给“拥堵型未来”增加了一条非常具体的非标准路径：

```text
沿海打工
-> 父母照护 + 女儿教育压力
-> 返乡
-> 用积蓄买车
-> 平台把本地陌生乘客变成可寻址需求
-> 用较长工作日换取时间安排弹性
```

不能把它推广成“网约车普遍实现返乡幸福就业”，但它证明平台匹配确实能让**一部分人把收入地点重新搬回家庭附近**。

### 9.4 “时间自由”与“平台可以强制你下线”可以同时成立

2019 年滴滴公开防疲劳驾驶规则：计费/服务时长达到一定阈值后，司机需要下线休息；短时策略包括累计服务 4 小时且无足够休息，需要下线 20 分钟，长时策略又按业务线设置 9—10 小时等阈值。

来源：

- 2019-06-18，北京日报 / 人民网：
  https://it.people.com.cn/n1/2019/0618/c1009-31165176.html

因此平台劳动的时间结构不是“没有老板 = 完全自由”，而是：

> **self-scheduled work inside server-enforced availability rules / 自我排班嵌套服务器可用性规则**。

这是很典型的拥堵型未来：选择变多，协调和治理层也变厚。

### 9.5 2019 北京夜间：地图上满是车标仍然可能没有一辆真正可用

2019 年降雪与节日叠加时，《新京报》记者在北京多个商圈测试：页面可见车辆图标，却长期没人接单；滴滴页面一度显示前面排队 228 人、预计等待 58 分钟。

来源：

- 2019-02-17，新京报 / 人民网：
  https://society.people.com.cn/n1/2019/0217/c1008-30758661.html

这给出一个极重要的界面考古边界：

> **car icon on map != executable supply**。

## 10. 2020—2022 的偶发型未来：订单历史突然从“商业记录”变成公共卫生接触轨迹

2020 年 1 月，新冠疫情早期，一名确诊患者曾使用网约车前往医院后，滴滴将相关司机暂停服务并配合隔离/调查，同时向有关部门提供订单相关信息；平台又为武汉特定日期的预约单提供取消政策。

来源：

- 2020-01-22，人民网 IT 频道，《滴滴回应武汉肺炎患者乘网约车就医》：
  https://it.people.com.cn/n1/2020/0122/c1009-31560403.html

证据等级：**B（平台回应经媒体报道）**。

这时出现了一个疫情前普通用户很少会主动思考的事实：

```text
order history
  = 商业结算记录
  + 司机劳动记录
  + 乘客移动轨迹
  + 潜在接触追踪线索
```

也就是说，同一个平台状态在灾害中会被重新征用为另一类基础设施。

### 10.1 市场匹配甚至可以临时切换为组织派车

2020 年武汉等地出现由网约车/出租车司机组成的社区保障车队。90 后司机尹兴山在同期采访中说，过去是司机等乘客，保障车队阶段则变成医务人员清晨在路边等他们，司机按社区需求承担固定保障任务。

来源：

- 2020-02-14，中国经济网 / 人民网：
  http://finance.people.com.cn/n1/2020/0214/c1004-31587285.html

证据等级：**B+（同期司机第一人称）**。

因此：

> **platform-mediated vehicle does not always mean market-dispatched vehicle**。

同一辆车可以从“接受陌生消费者订单”切换成“公共组织分配的应急运力”。

## 11. 2023—2026 的防守型未来：从“有没有车”变成“我是否愿意长期进入这个系统、以及不会用 App 的人还能不能叫到车”

### 11.1 供给过密以后，进入司机职业本身需要重新评估

2025 年《工人日报》报道，多地自 2023 年以来连续发布网约车市场饱和风险提示，有城市暂停或收紧新证办理。北京一名司机回忆，春节/元宵附近一天跑 15—16 小时，流水可超过千元，但之后同样长时间可能只有 500—600 元。

来源：

- 2025-02-28，《工人日报》/ 人民网：
  https://finance.people.com.cn/n1/2025/0228/c1004-40428476.html

2025 年另一篇报道还引用行业数据称，司机数量增长、平均小时收入下降，并采访到乘客遇到“司机接单后停在原地、联系不上，最后只能取消重新叫”的情况。

- 2025-10-20，中国青年报 / 人民网云南转载：
  https://yn.people.com.cn/n2/2025/1020/c378440-41384748.html

证据等级：**B（同期媒体；行业数量需保留原统计口径）**。

所以成熟平台阶段出现两条相反的状态：

```text
平台上司机很多
  != 某时某地乘客容易上车

平台容易注册/进入
  != 司机长期收入足以支持这条职业路径
```

这就是“防守型未来”的劳动版本：进入前越来越需要问**证照、车辆成本、空驶、平台费、小时收入、退出价值和还能否转行**。

### 11.2 老年人：数字平台成熟以后，城市又重新制造“物理叫车按钮”

2024 年北京已在 500 余个社区部署 1,500 多座助老打车站；对不会扫码叫车的老人，95128 电话专线继续存在。部分站点把当前位置直接用大字标出，老人可按键/电话叫车。

来源：

- 2024-01-09，北京市人民政府门户网站 / 北京日报：
  https://www.beijing.gov.cn/fuwu/bmfw/sy/jrts/202401/t20240109_3529605.html

另有社区物理终端能让老人一键呼叫出租车，并把医院目的地作为优先派单场景。

- 2024-01-17，北京日报 / 人民网北京：
  https://bj.people.com.cn/n2/2024/0117/c82838-40716700.html

这形成一个非常有意思的循环：

```text
街边身体扬招
-> 家中固定电话
-> Web 地址表单
-> 智能手机 GPS App
-> 为不会 App 的人重新落地成社区物理按钮
```

技术成熟并不总是把界面继续“虚拟化”。当数字入口成为基础设施以后，真正的普惠反而可能要求**把数字调度重新包装成最简单的物理接口**。

这可以称为：

> **interface re-materialization / 接口再物质化**。

## 12. 四种未来的对照

### 12.1 2005—2012：扩张型未来

核心问题：**以前要站路边碰运气的车，能不能提前找我？**

典型机制：电话、GPS、Web、短信、智能手机开始叠加；城市边缘、轮椅用户、赶时间者可以提前向系统发出需求；司机也开始从“巡游寻找客人”转向“先知道下一单可能在哪里”。

未来感偏向：

> 以后城市会越来越可调用，偏远一点、晚一点、临时一点，也不必完全靠运气。

### 12.2 2015—2019：拥堵型未来

核心问题：**当大家都进平台以后，谁得到订单、谁被看见、谁承担安全与劳动治理？**

典型机制：证照、价格、补贴、司机身份、人车一致、安全录音、行程分享、疲劳下线、供需动态定价。

未来感不再只是“能叫到车”，而是：

> 我有很多服务选项，但每个选项背后都有更多规则、身份、价格与协调劳动。

### 12.3 2020—2022：偶发型未来

核心问题：**当城市正常流动突然被公共卫生事件打断，平台车辆和订单数据库还能被重新组织成什么？**

订单可被取消、司机可被隔离、轨迹可参与流调、车辆可转为社区保障运力。

未来变成事件驱动：

> 明天能不能按今天的方式移动，不再被默认。

### 12.4 2023—2026：防守型未来

核心问题：**如何保留可用性，同时控制收入不确定、平台依赖、数字排斥和失灵风险？**

一边是司机进入已饱和市场前需要更谨慎；另一边是城市保留电话、巡游出租、社区一键按钮，避免“不会操作 App = 失去门到门交通”。

未来感偏向：

> 不再只追求更多订单/更多司机/更强 App，而是要保留退路、替代入口和可理解的成本。

## 13. 这条线改变了哪些重点矩阵

| 矩阵 | 新观察 |
|---|---|
| 就业 | 网约车形成返乡就业、阶段性劳动与平台化个体经营路径；“时间自由”与超长工作日可以同时存在。 |
| 住房 | 住在出租车自然巡游密度低的郊区，电话/App 调度能部分降低“必须住在交通主干线旁”的惩罚，但不能替代公共交通。 |
| 家庭/照护 | 轮椅老人、就医、父母照护让“车能不能直接到楼下”成为照护基础设施。 |
| 迁移 | 初到陌生城市的人不再需要先学会哪里有出租车站，定位和平台降低地方知识门槛。 |
| 非正规劳动 | 平台把私人车辆/个体司机纳入陌生人需求池，但劳动关系、证照、保险、社保边界继续变化。 |
| 长期中断 | 失去车辆、账号、证照或平台入口可以立即中断司机收入；疫情又可整体暂停常规匹配。 |
| 证件与记录 | 网约车驾驶员证、车辆记录、实名、人脸识别等把线下资格直接绑定到服务器接单权。 |
| 通信方式 | 电话话务员、短信、Web、GPS、App 是连续谱，不是手机 App 一夜替代所有旧渠道。 |
| 互联网平台 | 平台真正操作的不是“车”，而是请求、坐标、司机状态、匹配、价格、订单和结算记录。 |
| 信息获取 | 从看顶灯判断空车，转向看地图、ETA、车牌、司机头像；每个界面状态都可能与现实不同步。 |
| 社交关系 | 行程分享、紧急联系人让一次私人乘车可以临时把亲友纳入安全网络。 |
| 未来预期 | 2000s 想象是“车能到家门口”；2010s 是“任何时刻都能叫”；2020s 则越来越问“系统失灵时还有什么入口”。 |
| 线上/线下身份 | App 里的司机/车辆记录必须和现实到来的司机/车核对；不能默认二者天然一致。 |
| 平台消失与记忆 | 订单和轨迹具有高度隐私性，恰恰不适合被公共 archive 保存；历史研究容易只剩营销页和截图。 |

## 14. 最关键的 state gaps

后续所有出租车/网约车材料至少保留这些分界：

```text
registered vehicle != roadworthy/available vehicle
vehicle online != vacant
vacant != willing to accept
request sent != platform accepted
platform accepted != driver notified
notified != driver accepted
accepted != driver moving
GPS pin != legal/safe pickup point
ETA displayed != vehicle arrival
vehicle arrival != passenger recognizes vehicle
profile vehicle != physical vehicle
profile driver != physical driver
matched != boarded
boarded != trip started in system
route suggested != route actually driven
fare estimate != final fare
payment initiated != payment settled
completed order != physically completed trip
cancelled in passenger client != cancelled in every downstream system
platform ride record != public historical record
```

## 15. 反例与禁止过度解释

### 15.1 App 没有消灭扬招、出租车站、电话和公共交通

很多地方和时段，路边正好有空车时，扬招仍然是最低摩擦入口；地铁、公交、自行车和步行也可能比出租车更稳定、更便宜。

因此不能写：

> 网约车出现后所有城市移动都平台化。

### 15.2 “降低空驶”不是自动结果

司机去接远距离订单本身会产生 pickup deadheading；错误定位、乘客取消、司机取消和供需潮汐都能制造新的空驶。

### 15.3 “灵活就业”不能自动等于工作生活平衡

苏诗东能在家庭有事时少跑几单，同时也每天工作接近 12 小时。这两件事可以同时为真。

### 15.4 不能把极端安全事件代替所有行程

安全事件之所以留下大量新闻，是因为它们异常、严重、制度反应大。绝大多数普通的“十几分钟到家”反而不会形成公开档案。

### 15.5 不能用平台注册数/司机数直接推人口普及率或稳定职业数

一个人可在多个平台注册；注册司机不等于活跃司机；活跃司机也不等于全职司机。

## 16. 历史可见性：平台越成熟，真实的“那辆车有没有来”反而越难从 Web archive 回答

### 16.1 public shell / live geospatial state asymmetry

容易被保存的：

- 官网首页；
- “立即叫车”按钮；
- 价格说明；
- 下载页；
- 帮助文档；
- 新闻稿；
- 城市覆盖列表；
- App 截图。

最难被保存的：

- 2006-04-10 10:17 某地址 1.5 km 内究竟有哪些空车；
- 2013 某司机手机当时收到哪些订单；
- 2019 某商圈实时排队人数；
- 某一司机是否已点“接单”但尚未移动；
- 临时 ETA；
- 精确 GPS 轨迹；
- 乘客电话；
- 订单取消和退款原因。

因此 Web archive 更容易保存**邀请人叫车的壳**，而不是一次叫车真正成立的实时世界。

### 16.2 app binary / dispatch backend asymmetry

即使早期 Android APK/iOS 安装包被保存，今天运行它也可能因为：

- API host 已死；
- TLS/证书已过期；
- 旧地图 SDK 不可用；
- 登录接口迁移；
- 短信验证服务消失；
- 服务端不再理解旧协议；
- 司机端与乘客端需要同时有实时在线节点；

而无法复原当年的实际订单流。

所以：

> **client survival != service survival**。

### 16.3 订单数据库是更强证据，但隐私门槛也更高

若研究者真能拿到原始订单日志，确实可以回答等待时长、取消率、时空供需等问题；但它还可能包含家庭地址、医院、学校、夜间行程、手机号、司机身份和长期位置轨迹。

本仓后续原则应是：

> **不要为了“复原普通生活”而重新公开普通人的精确移动轨迹。**

优先使用已匿名聚合的研究数据、公开制度材料、用户自愿公开的同期叙述和不会重新识别个体的界面证据。

## 18. 尚未确定与下一步

1. 仍缺一组 **1990s 中国城市出租车电话/无线电调度的同期一手技术材料**，目前北京 1995 起点主要靠 2024 机构回顾。
2. 仍缺一份能明确区分 **车载 GPS“可定位”与“空重车状态实时上报”**的 2003–2006 原始设备/调度协议文档。
3. 2006 强生 `www.62580000.com` 的 Web 工作流有很强同期报道，但尚未在本轮取得合格的历史 Memento，不能据当前报道反推出当年 HTML/charset/browser/JS 细节。
4. 2012–2014 早期嘀嘀/快的客户端最好继续寻找精确版本 APK、帮助页或同期应用商店元数据，建立乘客端/司机端版本谱系。
5. 需要继续区分“出租车 App”与后来“私家车/快车/专车/顺风车”对象，不能把 2012 的 licensed taxi matching 倒写成后来完整 ride-hailing platform。
6. 未来若要量化“App 是否减少平均等待时间/空驶率”，必须取得可比的同城、同时段、同供给口径数据，不能拿平台 PR 数字直接做因果结论。

## 19. 它改变了我们对“人怎么活着”的哪一点理解

以前，一个人能不能临时离开某个地方，很大程度取决于**一辆空车是否碰巧从她眼前经过**。这对住在中心街道、身体方便、能在路边等待的人问题不大，却会惩罚住在边缘小区、坐轮椅、夜班下班、赶车赶飞机或带孩子的人。

电话调度第一次让“我需要一辆车”可以先于身体出现在路边；GPS 让调度员开始知道车在哪里；Web 把地址字符串直接送进车载终端；智能手机又让乘客和司机双方的位置持续进入同一个匹配系统。

但这条历史并没有从“不方便”直线走到“完美方便”。系统越成功，新的约束越明显：司机会选择哪些订单值得接，不用 App 的人可能发现路边空车不再停，定位点可能落在根本不能停车的位置，平台显示“已接单”也可能没人真正过来；司机自己则可能用每天十几个小时的劳动交换一种可以在家里有事时少跑几单的弹性。

所以这条生活史最终不是“出租车被互联网化”，而是：

> **城市里原本只能靠偶遇解决的一次会合，被一步步改造成可远程请求、可计算、可派发、可追踪的事务；而一个成熟城市真正需要保存的自由，是既能让车找到我，也不能让不会使用最新界面的人因此失去上车的资格。**
